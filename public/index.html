For teams running long-lived AI agents

The Fleet.

A technical breakdown of how Nova, Mira, and the rest of the fleet actually run — process model, MCP plumbing, memory, loops. Written so an engineer can replicate the parts that are useful, ignore the rest, and not have to reverse-engineer the live system.

00 · Intro

Why this exists.

The bet behind this document: a few AI agents that persist — that stay alive across days, hold their own memory, improve themselves nightly, and coordinate without a central brain — are worth more than a chat window you re-prompt from scratch every morning. Nova and Mira are two such agents, running in a fairly stable configuration on one Mac mini since early 2026, with Hermes as the substrate underneath them. This is a high-level exploration of how that actually works, written so a curious engineer can replicate the useful parts and stand up their own.

Most of what's interesting here isn't the model. It's the plumbing around the model: how a Claude process stays alive across days, how it gets work delivered to it, how it persists state, how two agents on the same machine coordinate, and how the operator notices when something is broken.

None of this is novel research. It's a particular composition of existing pieces — Claude Code, launchd, MCP, a PTY wrapper, a few shell scripts, a SQLite database, and the file system — that happens to be productive. If you wanted to stand up a similar fleet, you could.

What's not here Anything personal or sensitive — family, legal, the private project list, Telegram chat IDs, access tokens, customer or partner names. This document is bounded to the technical infrastructure any team might find useful. The companion repo follows the same boundary.
How to read this Three moves. First the why — this section. Then the how — §1 through §9, the technical guts, written for an engineer. Then bootstrap your own — §10–§12: the companion repo and the prompt you can hand a fresh Claude Code agent to stand up a starter fleet. The operating principles in §12 are the spine; if you read one section, read that one.
01 · Shape of the fleet

Two agents, one substrate, no tree.

There is no orchestrator. Nova and Mira are the two long-running agents. Hermes is the substrate they both run on — the nightly layer (§6) that improves the fleet itself rather than doing day-job work. Vellum is a fourth peer on a separate machine. None of them invokes the others as a boss; the human is the courier when handoffs happen.

Nova

Mac miniClaude Code · Opus

Long-running coding agent, built on a custom Claude Code setup (a PTY runner under launchd, see §2). Primary surface is Telegram. Owns: code production, deployment, multi-file refactors, day-job and personal site builds, peer review of Mira's work, briefing rituals.

Mira

Mac miniOpenClaw

Long-running ops + research agent, built on OpenClaw (a different runtime from Nova). Owns: infrastructure monitoring, content production, CRM data, SEO execution, publishing, daily-stats jobs. Has its own MCP gateway and its own cron stack.

Hermes

Mac miniSubstrate

The improvement substrate both agents run on — a peer, not a worker. Not a chat agent: a nightly cron pipeline that reads what the fleet did, plans what to surface, drafts contracts with falsifiable success criteria, and leaves each agent a curated brief. It improves the fleet rather than doing the day job. See §6.

Vellum

LaptopCodex

Deep-work executor on a separate machine. Reads a snapshot of the fleet's memory; writes back via a signed HTTP POST. Useful when a task needs web access or a larger context than is practical to keep warm on the mini.

Sub-agents

Ephemeral

Spawned by Nova or Mira inside their own process for a single task. Named (Ryn / Volt / Voss / Wren / etc.) so the operator can talk about them, but they aren't long-running. They die when the task is done.

The pattern that matters: two long-running agents and a shared improvement substrate on one host, plus on-demand sub-agents. The three different runtimes are deliberate — Nova on Claude Code, Mira on OpenClaw, Hermes as the cron substrate — because the failure modes differ and you don't want a single runtime bug to take the whole fleet down. Coordination is via files on a shared path, not a message bus. That's load-bearing — see §6 and §8.

02 · Process model

Keeping a Claude process alive for weeks.

A Claude Code process is a CLI invocation. By default it lives as long as the terminal that launched it. To get a long-running agent you need a supervisor that survives terminal closure, PTY allocation that satisfies Claude's interactive mode, and a clean restart story.

Nova's current process tree

launchd (com.nova.telegram) └─ python3 ~/.claude/nova-pty-runner.py └─ claude --dangerously-skip-permissions --channels plugin:telegram@claude-plugins-official └─ bun (MCP subprocess: plugin:telegram)

Why the layers

  1. launchd is the macOS process supervisor. A LaunchAgent plist registers the job under gui/<uid>, which restarts it on crash and survives login/logout. Run as a user-level agent, not a system daemon — these processes need user-keychain access and the same TCC permissions a desktop session has.
  2. PTY runner is a small Python script that allocates a pseudo-terminal, spawns Claude with that PTY as stdin/stdout, and re-pipes events. It exists because Claude's interactive mode wants a real TTY. The earlier shape was tmux; tmux died when the host's tmux server died. PTY runner is decoupled from tmux entirely.
  3. Claude CLI runs Claude with channels enabled. Inbound Telegram messages arrive via the channel; outbound goes through the MCP reply tool.
  4. bun (MCP server) is a child of the Claude process — the Telegram MCP plugin's runtime. If it dies, the Claude process stays alive but the channel goes mute. That's a known failure mode; the watchdog catches it (§7).

Restart command (for reference)

# Restart Nova's process tree end-to-end. launchd brings the runner
# back up, the runner respawns Claude, Claude respawns bun.
launchctl kickstart -k gui/$(id -u)/com.nova.telegram

# Inspect the live tree
pgrep -fl nova-pty-runner.py
pgrep -P $(pgrep -f nova-pty-runner) | xargs -I{} ps -fp {}

Mira runs a similar pattern but via the OpenClaw harness. Same principle (launchd supervises, sub-process owns the model, MCP servers attach as children).

Failure mode worth knowing The bun MCP subprocess can die silently while Claude keeps running. Symptom: the agent stops responding on Telegram but logs look normal. Fix: kickstart launchd, which tears down the whole tree. See scripts/nova-restart.sh in the companion repo.
03 · MCP wiring

How tools reach the model.

Every external system the agents touch — Telegram, Slack, Gmail, Drive, Supabase, Vercel, Fathom, internal queues — is wired as an MCP (Model Context Protocol) server. The agent doesn't talk to APIs directly; it calls tools the MCP server exposes.

What MCP gives you

  • Single auth boundary per service. The MCP server holds the credential; the agent gets a tool. If the token rotates, only the MCP server's env changes.
  • Schemas for free. Each tool declares its JSON schema. Claude validates calls against it. No drift between "what the docs say" and "what the model attempted."
  • Composition. A single agent can mount many servers. Nova mounts Telegram, Gmail, Drive, Vercel, Supabase, Slack, Fathom, Calendar, and a few internal ones.

Two flavors of MCP server in this fleet

FlavorExampleRuntimeAuth model
Hosted (claude.ai)gmail · drive · slack · supabase · vercelClaude.ai infrastructureOAuth via Claude account
Local pluginplugin:telegram@claude-plugins-officialbun subprocess on Mac miniBot token + access.json allowlist

Telegram channel binding (the one we lean on hardest)

Inbound Telegram messages arrive in the agent's context as <channel source="..." chat_id="..." message_id="..." user="..." ts="..."> blocks. The agent replies via the reply tool, passing chat_id back. Access is managed by a local file (~/.claude/channels/telegram/access.json), never by remote message — that's deliberate to prevent prompt-injection of allowlist changes.

Gotcha The MCP server runs as a child process of Claude. If you put your bot token in the wrong env file (e.g., ~/.zshrc instead of the launchd plist or ~/.claude/.mcp.json), the bun subprocess won't see it and the channel never binds. Symptom: agent comes up clean, Telegram drops messages silently. Hour-long debugging session waiting to happen.
04 · Memory architecture

What an agent remembers between sessions.

Claude's context window resets every conversation. To survive across sessions, agents read a memory directory before every turn. The memory is files on disk, indexed by a small synthesizer that prunes bloat.

File layout

~/.openclaw/workspace/memory/
  MEMORY.md                          # hand-curated index (≤150 lines)
  feedback_*.md                      # behavioral rules learned from corrections
  project_*.md                       # who/what/why for active initiatives
  reference_*.md                     # pointers to external systems
  user_*.md                          # facts about the operator

Every memory file is the same shape

---
name: deploy-requires-green-ci
description: short relevance hook used to decide whether to load this
metadata:
  type: feedback   # user · feedback · project · reference
---

Rule, fact, or pointer.

**Why:** the reason this matters (often an incident).
**How to apply:** when this guidance should kick in.

Cross-link other memories: [[other-memory-slug]]

Why a flat directory of files works

  • Auditable. Every memory is a git-able markdown file. You can git diff what changed between sessions.
  • Editable by hand. If the operator notices the agent has a wrong belief, they edit a file.
  • Composable. Nova and Mira walk each other's memory stores through a symmetric template — same frontmatter, same naming, same [[link]] resolver.
  • Synthesized, not appended. A nightly job rewrites MEMORY.md from the files; bloat goes to a dated archive. The index never grows monotonically.

The alternative — embeddings in a vector DB — is fine for some workloads but expensive for "what behavioral rule did the operator give me yesterday." Files win on auditability and round-tripping with humans.

For teams adopting this The companion repo includes scripts/memory-init.sh and a memory/ skeleton you can drop into any Claude-Code-based project. Same template Nova uses.
05 · Loop + harness

How non-trivial work actually gets done.

For anything that takes more than one turn, the agent writes a falsifiable assertion, runs an iteration, checks the assertion, decides next step. Three artifacts on disk. Resumable across context resets.

The three artifacts

FileOwnerPurpose
state.jsonThe loopSource of truth: what's the next step, what's been done, what's the last failure.
check-iteration.shHuman or agentDone-check script. Returns 0 if the current iteration passed. Never "looks good" — always greps for the assertion.
run-next-iteration.shHuman or agentReads state.json, executes next_step only, updates state, commits.

Worked example: a 12-step feature build

A recent feature (a property-listing hub on a production web app) was built as a 12-step loop:

  1. state.json tracked next_step (1 → 12), per-step done-check results, and any last failure.
  2. run-step.sh read state, looked up the step contract in dev-spec.md, and invoked Claude with the step contract as the prompt.
  3. handoffs/STEP-N.md were written at the end of each iteration so a fresh agent context could pick up cleanly.
  4. The done-check for each step was real: schema validation, curl + grep, type-check exit code, etc. Never "looks good."

Once the feature shipped and the reviewer signed off, the build-harness loop closed and its artifacts were deleted. A separate operational loop — weekly analytics ingest, a research sub-agent, safe changes applied automatically, an audit log — is built as scheduled-job infrastructure rather than a JSON file in the repo. Same pattern, different lifecycle (see the callout below).

Two different loops, often confused Build harness = transient, ships the feature, deleted when done. Operational loop = production scheduled job, runs forever. Same loop+harness pattern, different lifecycle.

Why this is worth adopting

  • Multi-iteration work survives context resets. The agent that finishes step 7 doesn't have to be the agent that started step 1.
  • Falsifiable done-checks force you to write the assertion before you write the code. That's the whole TDD thing dressed as a shell script.
  • One commit per step → readable git log, easy rollback, easy review.
06 · Hermes

The substrate: a nightly fleet improver.

Hermes is the third peer — the cron-driven substrate both Nova and Mira run on top of. It runs while everyone sleeps: watches what the fleet did during the day, decides what to surface next, drafts the asks, and leaves each agent a curated brief to start tomorrow with. Without Hermes the agents would still work — they'd just spend the first hour of each day figuring out what to work on, and nothing would systematically improve the fleet itself.

Pipeline shape

┌─────────────────────┐ │ activity-aggregator │ ← reads logs, receipts, git history, message buffer └──────────┬──────────┘ ▼ ┌─────────────────────┐ │ planner │ ← turns activity into proposed work items └──────────┬──────────┘ ▼ ┌─────────────────────┐ │ contract-creator │ ← writes each work item as a falsifiable contract └──────────┬──────────┘ ▼ ┌─────────────────────┐ │ executor │ ← runs contracts that don't need human approval └──────────┬──────────┘ ▼ ┌─────────────────────┐ │ qa-verifier + curator│ ← grades outputs, files acceptance, archives misses └──────────┬──────────┘ ▼ ┌─────────────────────┐ │ preflight-generator │ ← writes per-agent next-session briefings └─────────────────────┘

What lands on disk each night

ArtifactWhat it is
nova-queue.mdBacklog of contracts waiting for Nova to claim. The "what should I work on" list, ranked.
contracts/*.jsonOne file per work item. Each names: intent, falsifiable success criteria, owner, blocking-on, do-not-touch list.
plans/*.mdLonger-form plans the planner drafted — turned into contracts only when the contract-creator promotes them.
preflight-{agent}.md"Here's what's on your plate, here's what just broke, here's what's worth your attention" — injected at the start of the agent's next session.
deltas/, receipts/Audit trail. What each cron actually did, what changed, what was rejected.

Why a pipeline, not a single agent

  • Composable. Each stage is a small Python or bash script with a single responsibility. New stages bolt in without rewriting the orchestrator.
  • Restartable. Any stage can re-run on its inputs without re-doing prior stages. The state lives on disk, not in memory.
  • Watchable. Watchdogs run between stages — stall-watchdog.py, mira-watchdog.py, stakeholder-watcher.sh, business-outcome-probe.sh. They catch problems Hermes itself can't see.
  • Cron-friendly. Stages run on independent schedules. Activity aggregation runs every 15 minutes; the full planner runs nightly; preflight regenerates at 5am.

The acceptance gate

Contracts that the executor can't safely run alone (anything touching shared state, anything that costs money, anything novel) land in an approval queue rather than executing. The operator approves or rejects from the HTML brain (next section) — one click each — and the contract returns to the pipeline.

For teams adopting this The pattern that's portable: nightly cron pipeline that reads activity → drafts work → writes a curated brief. You don't need agents to benefit from this; even a daily "here's what changed in your repos + here's what's open in Linear + here's what merged that might affect you" cron is a useful version of the same idea.
07 · HTML brain

The operator's window into the fleet.

Everything Hermes produces is rendered to HTML at mira-artifacts — a private, auth-gated site that the operator opens to see fleet state, approve or reject contracts, read EOD reports, and reference the canonical design system. It's the only persistent UI in the whole system; Telegram is fast, but HTML is browsable.

What lives there

SurfaceWhat it shows
/index.htmlLanding — index of every artifact emitted today.
/dashboard/Live fleet dashboard. Active agents, in-flight contracts, recent failures.
/eod/{date}/End-of-day reports — what the fleet shipped, what's pending, what changed.
/fleet-{date}.htmlDaily fleet snapshot — header counts, contract burndown, watchdog state.
/briefs/Long-form analysis pieces (case briefs, marketing positioning, etc.) — generated by sub-agents.
/hermes/Hermes pipeline outputs — what was planned vs. what shipped.
/design-system.htmlThe Bauhaus design system you're looking at the descendant of right now. Canonical reference for all artifact rendering.

How approvals work

  1. Hermes drops a contract into the approval queue (rendered as a card in the dashboard).
  2. Operator opens mira-artifacts, clicks Approve or Reject.
  3. An Edge function (/api/approve) validates the bearer token and POSTs the decision back to the fleet decision tunnel.
  4. The next executor cron picks up the approved contract and runs it.

Auth

The whole site is gated by Edge Middleware that validates a key in the query string on first visit, sets an HTTP-only cookie good for 90 days, and redirects to a clean URL so the secret never lingers in the address bar. /api/health is intentionally public for uptime monitors. /api/approve, /api/contract-action, and /api/submit require a Bearer token (different from the cookie).

How content gets there

  • Git push. An agent (Mira, typically) renders HTML to a file under the right subdirectory, commits, pushes. Vercel auto-deploys on push to main. This is the path for anything we want a diff-able history of.
  • Direct API submit. Vellum (running on a separate machine) POSTs proposed content to /api/submit; it lands in a proposals branch for review rather than going straight to main.
  • One-shot ephemeral. vercel --prod from the project dir for artifacts we don't want in git history.
Why a separate site, not a SaaS The brain is small (a few hundred HTML files, a half-dozen Edge endpoints) and the data sensitivity is real. A static-site deploy with edge auth gives us no shared backend to harden, no third-party SaaS to audit, and no rendering complexity beyond "render markdown / json to HTML and push." Costs roughly nothing per month.
For teams adopting this You don't need the auth complexity if you start with a public scope. Static-site + nightly cron that renders the day's state to HTML + git push is enough for many "operator wants to see what's happening" use cases. Add Edge auth when you have data that justifies it.
08 · Coordination

Two agents on one host, no message bus.

Nova and Mira don't call each other. They share a filesystem and the human operator. That's it. Surprisingly robust for the work they do together.

Shared paths

~/.openclaw/workspace/
  memory/                            # symmetric memory store (both agents walk it)
  handoff-YYYY-MM-DD-{from}-to-{to}.md   # file-based async handoffs
  hermes-fleet-improver/             # shared nightly improvement pipeline
  intelligence/                      # shared data: SEO, monitoring, etc.

How a handoff looks in practice

  1. Mira finishes a YouTube production batch. Writes a handoff file naming what shipped and what's open.
  2. Operator sees the handoff (via daily digest) and routes the next move to Nova.
  3. Nova reads the handoff, picks up the open thread, writes its own response handoff when done.

No locks. No queues. No retry semantics. Two cooperating peers writing files in a shared directory.

The thing that makes this work is that the operator is in the loop. If the operator weren't routing, you'd need real coordination primitives. Because the operator routes, the agents can stay simple.

For teams adopting this If you wanted to add a third agent to this pattern, you'd add a directory and a memory namespace. You wouldn't add a message bus. Stay flat for as long as it stays useful.
09 · Heartbeat & watchdog

Noticing when the agent is broken.

Long-running agents fail in quiet ways. The MCP subprocess dies but the parent keeps running. The model returns text to the terminal instead of Telegram. State drifts. You need an explicit liveness signal and an explicit watchdog.

The pattern

  1. Heartbeat stamp. Every time the agent replies on Telegram, it runs date +%s > ~/.claude/nova-telegram-last-msg.txt. The PTY runner also stamps on detected output as a safety net.
  2. Watchdog cron. A separate process polls the stamp file. If the timestamp is older than threshold AND there's been an inbound message since the last reply, it fires.
  3. Watchdog action. First action is a Telegram alert to the operator. Restart is operator-initiated, not automatic — auto-restarting masks the root cause.

What we count as resource pressure

SIGTERM clusters on this host have historically tracked process count. The current contracts (open as of last review):

  • Pull ps aux | wc -l at every SIGTERM event going forward.
  • Audit and prune orphaned UID-501 processes (the user's UID).
  • Sub-agent spawn gate: halt new sub-agent spawns when process count crosses threshold (TBD — baseline still being measured).

None of this is rocket science. The point is that you write down "how do I notice when this is broken" as code, not as a vibe.

11 · Adopt this

What's actually worth lifting.

Not all of it. Adopt the parts that map to problems you have.

Worth adopting

  • The loop+harness pattern. Universal. Doesn't require Claude — works with any agent or even a human iterating.
  • File-based memory with synthesizer. Cheap, auditable, round-trips with humans.
  • launchd + PTY for long-running agents. Mac-specific but conceptually portable (systemd + pty on Linux).
  • Heartbeat + watchdog discipline. Cheap insurance against quiet failures.
  • Hermes-style nightly pipeline. Even without agents, a nightly "read activity → draft work → write a brief" cron beats starting every day from scratch.
  • HTML brain. A static-site + edge-auth + nightly render is enough for a real operator UI. No SaaS, no shared backend.

Probably not worth lifting

  • Two peer agents on one host. Only makes sense if you have two distinct workload personalities and a single human operator. Otherwise it's complexity for its own sake.
  • OpenClaw gateway (Mira's side). Useful for our shape, more than most teams need.
  • The agent buddies Telegram group. Operator UX for our specific cadence. You'd build your own.
  • Watchdog count (we run a lot). Start with one heartbeat + one watchdog. Earn the rest.

Smallest valuable adoption

  1. Pick one engineering task that benefits from multi-iteration work (a migration, a long-tail content port, a per-property sweep).
  2. Write a state.json, a check-iteration.sh, and a run-next-iteration.sh for it.
  3. Write a falsifiable done-check for each step.
  4. Run it. Notice that the agent (or you) can resume after any interruption without re-deriving where you were.
  5. Decide whether the rest of the fleet pattern is worth adopting.

If you do want to adopt more — the companion repo is the place to start, and Nova is available for pairing on Slack.

12 · Operating principles

The principles that keep it standing.

The architecture above is the easy half. The hard half is the handful of principles that keep a persistent fleet from quietly rotting — the failure modes that show up under real load, and the guardrails that answer them. This is the spine of the system; if the rest of the document is the body, this is what holds it upright. Cheap to copy, expensive to learn.

Pick the metric that tracks your contribution, not the noisy aggregate.

The fleet kept getting killed by host resource pressure. The first instinct was to gate on total process count — but that number is dominated by whatever desktop apps the operator happens to have open, so it tripped during normal work and missed real spikes. The signal that actually correlated with every incident was the count of processes the agents own. Gate on the axis you control, not the one that looks scary. A threshold on the wrong metric is worse than no threshold; it trains you to ignore the alarm.

When you ingest human feedback, read the surface humans actually use.

A watcher that collected feedback from a Slack channel pulled conversations.history and silently dropped every threaded reply — which is exactly where people were leaving their feedback. It looked like it was working (it appended messages, it had a checkpoint) while missing most of the input. Lesson: a pipeline that reads the wrong surface fails quietly. Verify you're capturing the channel people actually talk in, and test it with a real reply, not a synthetic one.

Never trust a status field. Verify the artifact it describes.

A pipeline reported "revision applied" on a document while the live document still had the old text. Elsewhere a job stamped a record "done" when the real work never ran. Status fields lie — they record intent, not outcome. The fix is boring and universal: before you believe "done," read the thing it claims to have changed. We now diff the live artifact, not the flag.

Encode the rule at the gate, once. Don't rely on catching it each time.

As more content started flowing through the fleet, the standards multiplied: style rules, voice-per-author, hard confidentiality lines (never expose a partner relationship in public material). Enforcing those by review-every-time doesn't scale and fails the one time attention slips. So they became hard-fail gates in the pipeline — a draft that violates one can't reach "ready," and a later edit can't quietly reintroduce it. Turn your most important "remember to…" into a check that runs whether or not anyone remembers.

Loops and harnesses are the default, not the exception.

Loop+harness (§5) isn't just for big multi-step work; it's the default for almost anything non-trivial. Write the falsifiable check first, change the artifact, keep the change only if the check improves, revert on regression. The discipline of stating the assertion up front catches more than the iteration loop itself does. The reflex — reach for a harness before editing — turns out to be the bottleneck, not the tooling.

This single host is the proving ground, not the destination.

Everything in §1–§11 runs on one Mac mini with two peers. That's deliberate: it's the cheapest place to learn the patterns. The next step is lifting them into a multi-tenant cloud platform — department-scoped agents, a shared memory service that enforces a structured-summary privacy contract (agents write summaries, never raw data, and the conductor only reads the summaries), per-agent identity at the gateway, and the nightly improver running as a managed job instead of a laptop cron. The architecture here is the rehearsal. The interfaces — file memory, loop+harness, heartbeat, the brief pipeline — are what survive the move; the single-host plumbing is what gets replaced.

The throughline Five of these six are the same lesson wearing different clothes: the system will tell you it's fine when it isn't. Wrong metric, unread thread, lying status, ungated rule, "looks good" instead of a check. The cheap defense is always the same — measure the thing you actually care about, and make the check run on its own.
