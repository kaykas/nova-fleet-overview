Mira Fleet Architecture.

A technical breakdown of how Mira and the rest of the fleet actually run — process model, MCP plumbing, layered memory, loops. A sanitized public reference so an engineer can replicate the useful parts, ignore the rest, and not have to reverse-engineer a live system.

00 · Intro

Why this exists.

The bet behind this document: a few AI agents that persist — that stay alive across days, hold their own memory, improve themselves nightly, and coordinate without a central brain — are worth more than a chat window you re-prompt from scratch every morning. Mira is the coordinator; specialist peers handle deeper workloads. Hermes is the substrate underneath them. This is a high-level breakdown of how that actually works, written so a curious engineer can replicate the useful parts and stand up their own.

Most of what's interesting here isn't the model. It's the plumbing around the model: how a Claude process stays alive across days, how it gets work delivered to it, how it persists state across multiple memory layers, how two agents on the same machine coordinate, and how the operator notices when something is broken.

None of this is novel research. It's a particular composition of existing pieces — Claude Code, launchd, MCP, a PTY wrapper, a few shell scripts, a vector store, and the file system — that happens to be productive. If you wanted to stand up a similar fleet, you could.

What's not here Anything personal or sensitive — operator names, company names, private project lists, chat IDs, access tokens, customer or partner names. This document is bounded to the technical infrastructure patterns any team might find useful. The companion repo follows the same boundary. See docs/privacy-checklist.md for what was deliberately omitted and why.
How to read this Three moves. First the why — this section. Then the how — §1 through §9, the technical guts, written for an engineer. Then bootstrap your own — §10–§12: the companion repo, the transferable quickstart, and the operating principles. The principles in §12 are the spine; if you read one section, read that one.
01 · Shape of the fleet

Mira coordinates. Peers specialize.

There is no orchestrator. Mira is the coordinator — the long-running ops and research agent. Specialist peers handle coding, builds, and deep-work. Hermes is the substrate both run on — the nightly layer (§6) that improves the fleet itself rather than doing day-job work. None of them invoke each other as a boss; the human operator is the courier when handoffs happen.

Mira — coordinator

Primary hostOpenClaw runtime

Long-running coordinator built on OpenClaw. Primary operator-facing surface is a chat channel. Owns: infrastructure monitoring, content production, analytics, publishing, daily-stats jobs, and cross-agent coordination. Has its own MCP gateway and its own cron stack.

Peer agent — specialist

Primary hostClaude Code

Long-running specialist agent built on a custom Claude Code setup (PTY runner under launchd, see §2). Owns: code production, deployment, multi-file refactors, peer review. Receives work via handoff files and the coordinator queue.

Hermes — substrate

Primary hostCron pipeline

The improvement substrate both agents run on — a peer, not a worker. Not a chat agent: a nightly cron pipeline that reads what the fleet did, plans what to surface, drafts contracts with falsifiable success criteria, and leaves each agent a curated brief. It improves the fleet rather than doing the day job. See §6.

Remote executor — deep-work

Secondary hostCodex / LLM

Deep-work executor on a separate machine. Reads a snapshot of the fleet's memory; writes back via a signed HTTP POST. Useful when a task needs web access or a larger context than is practical to keep warm on the primary host.

Sub-agents — ephemeral

Ephemeral

Spawned by the coordinator or peer agent inside their own process for a single task. Named so the operator can talk about them, but they aren't long-running. They die when the task is done.

The pattern that matters: a coordinator, one or more specialist peers, and a shared improvement substrate on one host, plus on-demand sub-agents. The two different runtimes (OpenClaw for coordinator, Claude Code for specialist) are deliberate — because the failure modes differ and you don't want a single runtime bug to take the whole fleet down. Coordination is via files on a shared path, not a message bus. That's load-bearing — see §6 and §8.

02 · Process model

Keeping a Claude process alive for weeks.

A Claude Code process is a CLI invocation. By default it lives as long as the terminal that launched it. To get a long-running agent you need a supervisor that survives terminal closure, PTY allocation that satisfies Claude's interactive mode, and a clean restart story.

The process tree

launchd (com.example.agent) ← user-level LaunchAgent └─ python3 agent-pty-runner.py ← PTY supervisor └─ claude --dangerously-skip-permissions --channels plugin:YOUR_CHANNEL_PLUGIN └─ bun (MCP subprocess: channel plugin)

Why the layers

  1. launchd is the macOS process supervisor. A LaunchAgent plist registers the job under gui/<uid>, which restarts it on crash and survives login/logout. Run as a user-level agent, not a system daemon — these processes need user-keychain access and the same TCC permissions a desktop session has.
  2. PTY runner (scripts/agent-pty-runner.py) is a small Python script that allocates a pseudo-terminal, spawns Claude with that PTY as stdin/stdout, and re-pipes events. It exists because Claude's interactive mode wants a real TTY. The earlier shape was tmux; tmux died when the host's tmux server died. PTY runner decouples entirely from tmux.
  3. Claude CLI runs Claude with channels enabled. Inbound messages arrive via the channel; outbound goes through the MCP reply tool.
  4. bun (MCP server) is a child of the Claude process — the channel MCP plugin's runtime. If it dies, the Claude process stays alive but the channel goes mute. Known failure mode; the watchdog catches it (§9).

Restart command

# Restart the agent's process tree end-to-end.
# launchd brings the runner back up, runner respawns Claude, Claude respawns bun.
launchctl kickstart -k gui/$(id -u)/com.example.agent

# Inspect the live tree
pgrep -fl agent-pty-runner.py
pgrep -P $(pgrep -f agent-pty-runner) | xargs -I{} ps -fp {}

Mira (coordinator) runs a similar pattern but via the OpenClaw harness. Same principle: a supervisor owns the process, sub-processes own the model connection and channel, child processes own MCP services.

Failure mode worth knowing The bun MCP subprocess can die silently while Claude keeps running. Symptom: the agent stops responding on the channel but logs look normal. Fix: kickstart launchd, which tears down the whole tree. See scripts/agent-restart.sh in the companion repo.

See docs/process-model.md for the full runbook including Linux port (systemd), all known failure modes, and the launchd plist reference.

03 · MCP wiring

How tools reach the model.

Every external system the agents touch is wired as an MCP (Model Context Protocol) server. The agent doesn't talk to APIs directly; it calls tools the MCP server exposes.

What MCP gives you

  • Single auth boundary per service. The MCP server holds the credential; the agent gets a tool. If the token rotates, only the MCP server's env changes.
  • Schemas for free. Each tool declares its JSON schema. The model validates calls against it.
  • Composition. A single agent can mount many servers: email, drive, messaging channel, analytics, deployment, internal queues — all as tools.

Two flavors of MCP server

FlavorExampleRuntimeAuth model
Hosted (via gateway)gmail · drive · slack · vercel · supabaseGateway infrastructureOAuth via LLM provider account
Local pluginplugin:channel@claude-plugins-officialbun subprocess on local hostBot token + access.json allowlist

Channel binding

Inbound messages arrive in the agent's context as <channel source="..." ...> blocks. The agent replies via the reply tool. Access is managed by a local file, never by remote message — that's deliberate to prevent prompt-injection of allowlist changes.

Gotcha The MCP server runs as a child process of Claude. If you put your token in the wrong env file (e.g., ~/.zshrc instead of the launchd plist or ~/.claude/.mcp.json), the bun subprocess won't see it and the channel never binds. Symptom: agent comes up clean, channel drops messages silently. Hour-long debugging session waiting to happen.
04 · Memory architecture

Layered memory that survives context resets.

Claude's context window resets every conversation. To survive across sessions, agents read a layered memory system before every turn. This isn't just a flat directory of files — it's a 10-layer architecture from fast boot context through long-term semantic storage, relationship graphs, and compressed project briefings.

The 10 memory layers

0
Boot context
Role file (AGENTS.md), soul/principles, hard-stop preflight, curated MEMORY.md index, today's raw log, active tasks, violation log (last 20).
Read: every session start, automatically
1
Flat-file memory
Typed markdown files: feedback_*.md, project_*.md, reference_*.md, user_*.md. Each has YAML frontmatter with name, type, and relevance hook.
Read: on demand, or via links in boot context
2
Daily raw log
memory/YYYY-MM-DD.md — raw session events, decisions, notes. Not curated; synthesizer compresses to Layer 1 entries nightly.
Read: boot (today + yesterday)
3
Semantic memory palace
SQLite + vector-embedding store, 9,000+ entries, shared across agents. Hierarchical: wing (domain) → room (topic) → hall (type: fact/event/decision/preference/advice/problem). Used for fuzzy recall of prior decisions, project history, contact facts.
Read: explicit search call — not auto-read at boot
4
Agent diaries
Per-agent append-only logs with tags and importance scores (1–5). Used for session reflections, pattern discovery, critical events.
Read: explicit query by tag or importance
5
Project memories
Memories tagged to named project buckets. Support timelines, summary views, and relationship graphs between project memories.
Read: explicit project query
6
Compressed context
Pre-computed AAAK-compressed representations of memory scopes (~30× smaller). Used for loading large memory windows efficiently into a single model call.
Read: explicit load for project briefings or handoffs
7
Relationship graph
Typed directed links between memories: related_to, causes, part_of, contradicts, updates, references. Traversable by hop count.
Read: traversal calls (get_related, get_memory_graph)
8
Handoff documents
Structured markdown: handoff-YYYY-MM-DD-{from}-to-{to}.md. Four sections: what I finished, what's open, what I'd like you to look at, anything fragile.
Read: next session start by receiving agent
9
Operational state
active-tasks.md, reminders.json, violation-log.md, autonomous-work-log.md, trigger-state.json.
Read: boot context

Flat-file memory shape

memory/
  MEMORY.md                          # hand-curated index (≤150 lines)
  feedback_*.md                      # behavioral rules from corrections
  project_*.md                       # who/what/why for active initiatives
  reference_*.md                     # pointers to external systems
  user_*.md                          # facts about the operator

Every memory file is the same shape

---
name: deploy-requires-green-ci
description: short relevance hook used to decide whether to load this
metadata:
  type: feedback   # user · feedback · project · reference
---

Rule, fact, or pointer.

**Why:** the reason this matters (often an incident).
**How to apply:** when this guidance should kick in.

Cross-link other memories: [[other-memory-slug]]

Why flat files for the base layer

  • Auditable. Every memory is a git-able markdown file. You can git diff what changed between sessions.
  • Editable by hand. If the operator notices the agent has a wrong belief, they edit a file.
  • Composable. Multiple agents walk the same store via a symmetric template — same frontmatter, same naming, same [[link]] resolver.
  • Synthesized, not appended. A nightly job rewrites MEMORY.md from the files; bloat goes to a dated archive. The index never grows monotonically.

Memory write discipline

Hard rule: search before claiming you don't know. Before saying "I have no context on X," search the memory palace. A 9,000+ entry palace is useless if you don't query it. Skipping this when memories exist is a protocol violation.

Write targets by type:

WhatWhere
Hard rules / lessons learnedLESSONS_LEARNED.md
Operational stateEOD block in MEMORY.md
Durable factsFlat-file + memory palace (both — palace alone not read at boot)
Project decisionsProject memory entry + wiki page
Session eventsmemory/YYYY-MM-DD.md
Important eventsAgent diary (importance ≥ 4)
For teams adopting this Start with Layer 0–2 (boot context + flat files + daily log). That's enough for a single agent to maintain continuity across sessions. Add the semantic palace (Layer 3) when you have more than a few dozen memories and fuzzy recall becomes useful. Layers 4–9 are optimizations; earn them.
Quickstart scripts/memory-init.sh path/to/project creates a memory/ dir with the canonical template and a starter MEMORY.md. See examples/memory/ for working examples of each file type including daily-log, active-tasks, and handoff templates.
05 · Loop + harness

How non-trivial work actually gets done.

For anything that takes more than one turn, the agent writes a falsifiable assertion, runs an iteration, checks the assertion, decides next step. Three artifacts on disk. Resumable across context resets.

The three artifacts

FileOwnerPurpose
state.jsonThe loopSource of truth: what's the next step, what's been done, what's the last failure.
check-iteration.shHuman or agentDone-check script. Returns 0 if the current iteration passed. Never "looks good" — always greps for the assertion.
run-next-iteration.shHuman or agentReads state.json, executes next_step only, updates state, commits.

Worked example: a 12-step feature build

A recent feature build was driven as a 12-step loop:

  1. state.json tracked next_step (1 → 12), per-step done-check results, and any last failure.
  2. run-step.sh read state, looked up the step contract in dev-spec.md, and invoked the agent with the step contract as the prompt.
  3. handoffs/STEP-N.md were written at the end of each iteration so a fresh agent context could pick up cleanly.
  4. The done-check for each step was real: schema validation, curl + grep, type-check exit code. Never "looks good."

Once the feature shipped, the build-harness loop closed and its artifacts were deleted. A separate operational loop — periodic analytics ingest, a research sub-agent, safe changes applied automatically, an audit log — is built as scheduled-job infrastructure rather than a JSON file in the repo. Same pattern, different lifecycle.

Two different loops, often confused Build harness = transient, ships the feature, deleted when done. Operational loop = production scheduled job, runs forever. Same loop+harness pattern, different lifecycle.

Why this is worth adopting

  • Multi-iteration work survives context resets. The agent that finishes step 7 doesn't have to be the agent that started step 1.
  • Falsifiable done-checks force you to write the assertion before you write the code. That's TDD dressed as a shell script.
  • One commit per step → readable git log, easy rollback, easy review.

See docs/loop-harness-pattern.md for the full pattern with worked example, state.json schema, and check-iteration.sh shape.

06 · Hermes substrate

The nightly fleet improver.

Hermes is the substrate both agents run on — a peer, not a worker. It runs while everyone sleeps: watches what the fleet did during the day, decides what to surface next, drafts falsifiable contracts, and leaves each agent a curated brief to start tomorrow with. Without Hermes the agents still work — they'd just spend the first hour figuring out what to work on, and nothing would systematically improve the fleet itself.

Pipeline shape

┌─────────────────────┐ │ activity-aggregator │ ← reads logs, receipts, git history, message buffer └──────────┬──────────┘ ▼ ┌─────────────────────┐ │ planner │ ← turns activity into proposed work items └──────────┬──────────┘ ▼ ┌─────────────────────┐ │ contract-creator │ ← writes each work item as a falsifiable contract └──────────┬──────────┘ ▼ ┌─────────────────────┐ │ executor │ ← runs contracts that don't need human approval └──────────┬──────────┘ ▼ ┌─────────────────────┐ │ qa-verifier+curator │ ← grades outputs, files acceptance, archives misses └──────────┬──────────┘ ▼ ┌─────────────────────┐ │ preflight-generator │ ← writes per-agent next-session briefings └─────────────────────┘

What lands on disk each night

ArtifactWhat it is
coordinator-queue.mdBacklog of contracts waiting for the coordinator to claim. The "what should I work on" list, ranked.
contracts/*.jsonOne file per work item. Each names: intent, falsifiable success criteria, owner, blocking-on, do-not-touch list.
plans/*.mdLonger-form plans the planner drafted — turned into contracts only when the contract-creator promotes them.
preflight-{agent}.md"Here's what's on your plate, here's what just broke, here's what's worth your attention" — injected at the start of the agent's next session.
deltas/, receipts/Audit trail. What each cron actually did, what changed, what was rejected.

Why a pipeline, not a single agent

  • Composable. Each stage is a small Python or bash script with a single responsibility. New stages bolt in without rewriting the orchestrator.
  • Restartable. Any stage can re-run on its inputs without re-doing prior stages. State lives on disk, not in memory.
  • Watchable. Watchdogs run between stages and catch problems Hermes itself can't see.
  • Cron-friendly. Stages run on independent schedules. Activity aggregation runs every 15 minutes; the full planner runs nightly; preflight regenerates at 5am.

The acceptance gate

Contracts the executor can't safely run alone (anything touching shared state, anything that costs money, anything novel) land in an approval queue rather than executing. The operator approves or rejects from the HTML brain (next section) — one click each.

For teams adopting this The portable pattern: nightly cron pipeline that reads activity → drafts work → writes a curated brief. You don't need agents to benefit. Even a daily "here's what changed in your repos + here's what's open in your tracker + here's what merged that might affect you" cron is a useful version of the same idea.
07 · HTML brain

The operator's window into the fleet.

Everything Hermes produces is rendered to HTML at a private, auth-gated site — the operator opens it to see fleet state, approve or reject contracts, read EOD reports, and reference the canonical design system. It's the only persistent UI in the system; the chat channel is fast, but HTML is browsable.

What lives there

SurfaceWhat it shows
/index.htmlLanding — index of every artifact emitted today.
/dashboard/Live fleet dashboard. Active agents, in-flight contracts, recent failures.
/eod/{date}/End-of-day reports — what the fleet shipped, what's pending, what changed.
/fleet-{date}.htmlDaily fleet snapshot — header counts, contract burndown, watchdog state.
/hermes/Hermes pipeline outputs — what was planned vs. what shipped.
/api/approveBearer-auth approve/reject endpoint for contracts.
/api/healthIntentionally public health check for uptime monitors.

How approvals work

  1. Hermes drops a contract into the approval queue (rendered as a card in the dashboard).
  2. Operator opens the brain site, clicks Approve or Reject.
  3. An Edge function validates the bearer token and POSTs the decision back to the fleet decision tunnel.
  4. The next executor cron picks up the approved contract and runs it.

Auth

The whole site is gated by Edge Middleware that validates a key in the query string on first visit, sets an HTTP-only cookie good for 90 days, and redirects to a clean URL so the secret never lingers in the address bar. /api/health is intentionally public. Mutating endpoints require a Bearer token (different from the cookie).

How content gets there

  • Git push. An agent renders HTML, commits, pushes; Vercel auto-deploys on push to main. This is the path for anything we want a diff-able history of.
  • Direct API submit. Remote executors POST proposed content to /api/submit; it lands in a proposals branch for review.
  • One-shot ephemeral. vercel --prod from the project dir for artifacts we don't want in git history.
For teams adopting this Start public: static-site + nightly cron that renders the day's state to HTML + git push. No SaaS, no shared backend. Add Edge auth when you have data that justifies it.
08 · Coordination

Two agents on one host, no message bus.

Mira and the peer specialist don't call each other. They share a filesystem and the human operator. That's it. Surprisingly robust for the work they do together.

Shared paths

~/.openclaw/workspace/          # or your equivalent shared workspace root
  memory/                       # symmetric memory store (both agents walk it)
  handoff-YYYY-MM-DD-{from}-to-{to}.md   # file-based async handoffs
  fleet-improver/               # shared nightly improvement pipeline
  intelligence/                 # shared data: analytics, monitoring, etc.

How a handoff looks in practice

  1. One agent finishes a batch. Writes a handoff file naming what shipped and what's open.
  2. Operator sees the handoff (via daily digest) and routes the next move to the other agent.
  3. Receiving agent reads the handoff, picks up the open thread, writes its own response handoff when done.

No locks. No queues. No retry semantics. Two cooperating peers writing files in a shared directory.

The thing that makes this work is that the operator is in the loop. If the operator weren't routing, you'd need real coordination primitives. Because the operator routes, the agents can stay simple.

For teams adopting this If you wanted to add a third agent to this pattern, you'd add a directory and a memory namespace. You wouldn't add a message bus. Stay flat for as long as it stays useful. See docs/coordination.md for when you'd need to graduate to real coordination primitives.
09 · Heartbeat & watchdog

Noticing when the agent is broken.

Long-running agents fail in quiet ways. The MCP subprocess dies but the parent keeps running. The model returns text to the terminal instead of the channel. State drifts. You need an explicit liveness signal and an explicit watchdog.

The pattern

  1. Heartbeat stamp. Every time the agent replies on the channel, it runs date +%s > ~/.claude/agent-last-output.txt. The PTY runner also stamps on detected output as a safety net.
  2. Watchdog cron. A separate process polls the stamp file. If the timestamp is older than threshold AND there's been an inbound message since the last reply, it fires.
  3. Watchdog action. First action is an alert to the operator. Restart is operator-initiated, not automatic — auto-restarting masks the root cause.

What we count as resource pressure

Host resource pressure incidents have historically correlated with agent-owned process count, not total host process count. The right threshold is gated on the axis you control: agent-owned processes, not whatever desktop apps the operator happens to have open.

None of this is rocket science. The point is that you write down "how do I notice when this is broken" as code, not as a vibe.

See scripts/heartbeat-watchdog.sh for a reference implementation.

11 · Adopt this

What's actually worth lifting.

Not all of it. Adopt the parts that map to problems you have.

Worth adopting

  • The loop+harness pattern. Universal. Doesn't require Claude — works with any agent or even a human iterating.
  • Layered memory architecture. Start with boot context + flat files; add semantic palace when you have scale to justify it.
  • launchd + PTY for long-running agents. Mac-specific but conceptually portable (systemd + pty on Linux).
  • Heartbeat + watchdog discipline. Cheap insurance against quiet failures.
  • Hermes-style nightly pipeline. Even without agents, a nightly "read activity → draft work → write a brief" cron beats starting every day from scratch.
  • HTML brain. Static-site + edge-auth + nightly render is enough for a real operator UI.

Probably not worth lifting first

  • Two peer agents on one host. Only makes sense if you have two distinct workload personalities and a single human operator.
  • OpenClaw gateway. Useful for this fleet's shape; more than most teams need to start.
  • All 9 watchdogs. Start with one heartbeat + one watchdog. Earn the rest.
  • Full semantic palace. Add after flat-file layer is working. The palace is a force-multiplier, not a starting point.

Smallest valuable adoption

  1. Pick one engineering task that benefits from multi-iteration work (a migration, a long-tail content port, a per-property sweep).
  2. Write a state.json, a check-iteration.sh, and a run-next-iteration.sh for it.
  3. Write a falsifiable done-check for each step.
  4. Run it. Notice that the agent (or you) can resume after any interruption without re-deriving where you were.
  5. Decide whether the rest of the fleet pattern is worth adopting.
12 · Operating principles

The principles that keep it standing.

The architecture above is the easy half. The hard half is the handful of principles that keep a persistent fleet from quietly rotting — the failure modes that show up under real load, and the guardrails that answer them. This is the spine of the system. Cheap to copy, expensive to learn.

Pick the metric that tracks your contribution, not the noisy aggregate.

The fleet kept getting killed by host resource pressure. The first instinct was to gate on total process count — but that number is dominated by whatever desktop apps the operator happens to have open. The signal that actually correlated with every incident was the count of processes the agents own. Gate on the axis you control. A threshold on the wrong metric is worse than no threshold; it trains you to ignore the alarm.

When you ingest human feedback, read the surface humans actually use.

A watcher that collected feedback from a messaging channel pulled the main history and silently dropped every threaded reply — which is exactly where people were leaving their feedback. It looked like it was working while missing most of the input. A pipeline that reads the wrong surface fails quietly. Verify you're capturing the channel people actually talk in, and test it with a real reply.

Never trust a status field. Verify the artifact it describes.

A pipeline reported "revision applied" while the live document still had the old text. Status fields record intent, not outcome. Before you believe "done," read the thing it claims to have changed. We now diff the live artifact, not the flag.

Encode the rule at the gate, once. Don't rely on catching it each time.

As more content started flowing through the fleet, the standards multiplied: style rules, voice-per-author, hard confidentiality lines. Enforcing those by review-every-time doesn't scale and fails the one time attention slips. They became hard-fail gates in the pipeline — a draft that violates one can't reach "ready." Turn your most important "remember to…" into a check that runs whether or not anyone remembers.

Loops and harnesses are the default, not the exception.

Loop+harness (§5) isn't just for big multi-step work; it's the default for almost anything non-trivial. Write the falsifiable check first, change the artifact, keep the change only if the check improves, revert on regression. The reflex — reach for a harness before editing — turns out to be the bottleneck, not the tooling.

This single host is the proving ground, not the destination.

Everything in §1–§11 runs on one host with two or three peers. That's deliberate: it's the cheapest place to learn the patterns. The next step is lifting them into a multi-tenant platform — department-scoped agents, a shared memory service, per-agent identity at the gateway, and the nightly improver running as a managed job. The interfaces — file memory, loop+harness, heartbeat, the brief pipeline — are what survive the move; the single-host plumbing is what gets replaced.

The throughline Five of these six are the same lesson wearing different clothes: the system will tell you it's fine when it isn't. Wrong metric, unread thread, lying status, ungated rule, "looks good" instead of a check. The cheap defense is always the same — measure the thing you actually care about, and make the check run on its own.
